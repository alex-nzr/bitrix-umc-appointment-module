# Тест-кейсы для модуля `anz.appointment`

Этот файл предназначен для ручного тестирования модуля записи на приём и React-расширения `form-react`.

## Цель тестирования

Проверить:

- корректность работы формы записи на приём;
- согласованность фронтенда и backend-контроллера;
- работу настроек модуля;
- корректность бронирования, подтверждения и отправки заявки;
- корректность email-уведомлений;
- открытие формы как через стандартную кнопку, так и через пользовательскую кнопку.

## Что должно быть подготовлено перед тестом

Перед началом тестирования убедитесь, что:

1. Модуль установлен и подключён.
2. В настройках модуля заполнены доступы к 1С.
3. Обмен с 1С работает и справочники клиник, врачей, услуг и расписания доступны.
4. Для React-формы выбрано расширение `anz.appointment.form-react`.
5. После последних изменений пересобран фронтенд `install/js/form-react/build`.
6. На тестовой странице выведена форма записи или подключено расширение открытия формы.
7. Есть хотя бы:
   - одна клиника;
   - один врач;
   - одна доступная дата;
   - один свободный слот;
   - при включённых услугах хотя бы одна услуга у врача.

## Общие правила проверки

При каждом сценарии проверяйте:

- нет ли ошибок в консоли браузера;
- нет ли ошибок ответа AJAX;
- корректно ли отображаются тексты ошибок в интерфейсе;
- не зависает ли форма в состоянии загрузки;
- не ломается ли переход между шагами;
- не остаётся ли форма в неконсистентном состоянии после закрытия или возврата назад.

## Базовый позитивный сценарий записи без подтверждения

### Предусловия

- в настройках модуля выбран React-виджет;
- подтверждение отключено;
- услуги либо включены, либо выключены;
- email-уведомление можно тестировать отдельно.

### Шаги

1. Открыть форму записи.
2. Выбрать клинику.
3. Выбрать специализацию.
4. Выбрать врача или услугу, в зависимости от текущего режима.
5. Выбрать дату.
6. Выбрать свободный слот.
7. Заполнить контактные данные.
8. Нажать кнопку записи.

### Ожидаемый результат

- слот успешно бронируется;
- заявка успешно отправляется;
- форма переходит на финальный экран;
- на финальном экране отображаются врач, дата и время;
- в консоли браузера нет ошибок;
- контроллер `sendAppointmentAction` возвращает успешный ответ.

## Сценарий записи с подтверждением по телефону

### Предусловия

- в настройках модуля включено подтверждение по телефону.

### Шаги

1. Открыть форму записи.
2. Пройти шаги выбора клиники, врача, услуги и времени.
3. На шаге контактов ввести телефон.
4. Перейти на шаг подтверждения.
5. Убедиться, что отправляется код подтверждения.
6. Ввести корректный код.
7. Подтвердить код.

### Ожидаемый результат

- код отправляется без ошибок;
- таймер обратного отсчёта запускается;
- при успешной проверке кода создаётся запись;
- после успешной записи открывается финальный экран;
- если email-уведомления включены и email указан, дополнительно отправляется email.

## Сценарий записи с подтверждением по email

### Предусловия

- в настройках модуля включено подтверждение по email.

### Шаги

1. Открыть форму записи.
2. Пройти шаги выбора записи.
3. На шаге контактов заполнить email.
4. Перейти к подтверждению.
5. Получить код из email.
6. Ввести код подтверждения.
7. Подтвердить.

### Ожидаемый результат

- код отправляется на email;
- форма принимает код;
- после подтверждения создаётся запись;
- открывается финальный экран;
- при включённых email-уведомлениях отправляется письмо о записи.

## Сценарий проверки email-уведомления о созданной записи

### Предусловия

- в настройках модуля включена опция email-уведомления;
- в форме введён email пользователя.

### Шаги

1. Создать запись любым успешным сценарием.
2. Дождаться финального экрана.
3. Проверить, было ли отправлено письмо.

### Ожидаемый результат

- `sendAppointment` завершается успешно;
- после него вызывается отправка email-уведомления;
- запись не считается неуспешной, если email-уведомление не отправилось;
- при штатной работе письмо приходит на email пользователя.

## Сценарий проверки отсутствия email-уведомления при выключенной опции

### Предусловия

- в настройках модуля опция email-уведомления выключена.

### Шаги

1. Успешно создать запись.
2. Проверить итоговый результат.

### Ожидаемый результат

- запись создаётся;
- письмо не отправляется;
- финальный экран показывается как обычно.

## Сценарий отображения логотипа

### Предусловия

- в настройках модуля загружен логотип.

### Шаги

1. Открыть форму записи.

### Ожидаемый результат

- в верхней части формы отображается логотип;
- логотип не ломает вёрстку на desktop и mobile;

## Сценарий стандартной кнопки открытия формы

### Предусловия

- отключено использование пользовательской кнопки.

### Шаги

1. Открыть страницу с виджетом.

### Ожидаемый результат

- отображается стандартная кнопка открытия формы;
- по клику форма открывается;
- по повторному взаимодействию форма работает корректно.

## Сценарий пользовательской кнопки открытия формы

### Предусловия

- включена опция использования собственной кнопки;
- задан CSS-селектор;
- на странице есть элементы, подходящие под этот селектор.

### Шаги

1. Открыть страницу.
2. Убедиться, что стандартная кнопка не отображается.
3. Нажать на пользовательскую кнопку.

### Ожидаемый результат

- стандартная кнопка отсутствует;
- форма открывается по клику на пользовательский элемент;
- если на странице несколько элементов с этим селектором, форма открывается по каждому из них.

## Сценарий пользовательской кнопки при неверном селекторе

### Предусловия

- включена пользовательская кнопка;
- указан селектор, по которому на странице нет элементов.

### Шаги

1. Открыть страницу.

### Ожидаемый результат

- стандартная кнопка не рисуется;
- форма не открывается автоматически;
- вёрстка страницы не ломается;
- в консоли нет критических ошибок, из-за которых падает приложение.

## Сценарий работы при выключенных услугах

### Предусловия

- в настройках модуля услуги выключены.

### Шаги

1. Открыть форму.
2. Выбрать клинику и специализацию.
3. Выбрать врача.
4. Перейти к выбору времени.
5. Забронировать слот и завершить запись.

### Ожидаемый результат

- форма не требует выбора услуги;
- бронирование слота работает;
- запись создаётся без выбора услуги;
- финальный экран открывается корректно.

## Сценарий работы при включённых услугах

### Предусловия

- в настройках модуля услуги включены;
- у выбранного врача есть услуги.

### Шаги

1. Открыть форму.
2. Выбрать клинику и специализацию.
3. Выбрать врача.
4. Выбрать одну или несколько услуг.
5. Перейти к выбору времени.

### Ожидаемый результат

- без выбора услуги переход дальше невозможен;
- после выбора услуги доступны только валидные варианты врача/слотов;
- длительность слотов рассчитывается корректно.

## Сценарий проверки длительности слотов

### Предусловия

- у врача есть услуга с персональной длительностью;
- либо у услуги задана длительность в общем списке.

### Шаги

1. Выбрать врача и услугу с известной длительностью.
2. Перейти к выбору времени.
3. Проверить длину и разбивку слотов.

### Ожидаемый результат

- если у врача для услуги задана `personalDuration`, используется она;
- если у врача длительность не задана или равна нулю, берётся длительность из услуги;
- если нет ни того, ни другого, используется fallback-значение из backend;
- слоты не перекрываются и не имеют отрицательной или нулевой длины.

## Сценарий смены выбранного слота

### Предусловия

- слот уже выбран и предварительно забронирован.

### Шаги

1. Выбрать один слот.
2. Затем выбрать другой слот того же врача.

### Ожидаемый результат

- ранее выбранный слот освобождается;
- новая бронь создаётся успешно;
- в store и UI отображается только новый слот;
- не возникает ошибки отмены брони.

## Сценарий закрытия формы до завершения записи

### Предусловия

- пользователь уже выбрал слот и бронь создана, но запись ещё не отправлена окончательно.

### Шаги

1. Выбрать слот.
2. Закрыть форму крестиком или через закрытие диалога.

### Ожидаемый результат

- бронь слота отменяется;
- форма закрывается;
- внутреннее состояние формы сбрасывается;
- при повторном открытии форма начинается с первого шага.

## Сценарий возврата назад после ошибки подтверждения или записи

### Шаги

1. Дойти до шага подтверждения.
2. Ввести неверный код или смоделировать ошибку создания записи.
3. Нажать кнопку возврата назад.

### Ожидаемый результат

- отображается понятная ошибка;
- форма не зависает;
- пользователь может вернуться на предыдущий шаг и выбрать другое время или повторить попытку.

## Негативный сценарий: нет доступных слотов

### Шаги

1. Выбрать врача и услуги для случая, когда свободных слотов нет.

### Ожидаемый результат

- календарь и список слотов не ломаются;
- пользователь видит сообщение, что доступных слотов нет;
- переход дальше невозможен.

## Негативный сценарий: ошибка загрузки клиник, врачей, услуг или расписания

### Шаги

1. Смоделировать ошибку backend-ответа или недоступность 1С.
2. Открыть форму и пройти до проблемного шага.

### Ожидаемый результат

- в интерфейсе показывается сообщение об ошибке;
- приложение не падает;
- повторное открытие формы не приводит к поломанному состоянию.

## Негативный сценарий: ошибка email-уведомления

### Предусловия

- запись создаётся успешно;
- отправка email-уведомления падает.

### Шаги

1. Выполнить успешную запись с включённой опцией email.
2. Смоделировать ошибку отправки письма.

### Ожидаемый результат

- сама запись остаётся успешной;
- пользователь видит финальный экран;
- в консоли может быть сообщение об ошибке отправки письма, но UI не переходит в ошибочное состояние.

## Сценарий проверки событий и кастомных полей 1С

### Предусловия

- в тестовой 1С есть хотя бы одно кастомное поле в ответе клиник, сотрудников, услуг или расписания;
- зарегистрирован тестовый обработчик одного из событий `onAfter...Parsed`.

### Шаги

1. В обработчике события получить массив данных из `$event->getParameters()`.
2. Проверить, что неизвестные поля из 1С доступны в ключе `_extra`.
3. Вернуть из обработчика `\Bitrix\Main\EventResult` с дополнительным тестовым полем.
4. Открыть форму записи и пройти шаги загрузки справочников и расписания.

### Ожидаемый результат

- события `onBefore...Parsed` вызываются, но используются только для диагностики и совместимости;
- события `onAfter...Parsed` позволяют изменить массив данных;
- данные из `_extra` не теряются и после ответа backend доступны фронтенду в ключе `extra`;
- пользовательский сценарий записи продолжает работать без ошибок.

## Проверка адаптивности

### Шаги

1. Открыть форму на desktop.
2. Открыть форму в mobile-ширине.

### Ожидаемый результат

- логотип, шаги, календарь, слоты и формы читаемы;
- диалог корректно открывается в full-screen на мобильных;
- кнопки и поля не выходят за границы экрана.

## Что дополнительно проверить после каждого релиза

- корректность открытия формы со стандартной кнопки;
- корректность открытия формы через пользовательский селектор;
- создание записи без подтверждения;
- создание записи с подтверждением;
- отправку email-уведомления;
- корректную отмену брони при закрытии формы;
- корректную работу при включённых и выключенных услугах;
- отсутствие ошибок в консоли браузера и в AJAX-ответах.
